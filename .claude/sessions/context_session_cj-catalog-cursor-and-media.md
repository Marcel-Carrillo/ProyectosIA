## Summary

This is a backend-only fast-follow to `cj-catalog-auto-provisioning` (already in production), fixing two real bugs discovered live:

1. **No sync cursor**: `CjCatalogSyncService.syncCatalog` (`backend/src/application/services/cjCatalogSyncService.ts:48-177`) always starts at `page = 1`. Every scheduled run re-syncs the same ~100 products forever. Fix: persist a cursor (`SupplierIntegration.catalogSyncCursorPage`/`catalogSyncTotalPages`/`catalogSyncWrappedAt` — new Prisma migration) so each run continues where the last left off, wrapping to page 1 once the catalog end is reached.
2. **No image/data capture**: `CjCatalogPromotionService.promote()` (`backend/src/application/services/cjCatalogPromotionService.ts:173-225`) never creates `ProductImage` or sets `Product.mainImageUrl`, even though CJ's real API returns image URLs (`product.bigImage`, `variant.variantImage`) already stored verbatim in `CjCatalogItem.rawPayload` (confirmed live in production). Fix: extend `CjProductDto`/`CjVariantDto` (`backend/src/infrastructure/external/cjTypes.ts`) with these fields, add a shared `extractCjImages(rawPayload)` helper, wire it into `promote()`'s existing transaction, and add a one-off backfill script for the ~100 products already promoted in production without images.

## Key design decisions already made (do not relitigate — implement per these)

- **D1 (cursor)**: page-number cursor on `SupplierIntegration`, NOT a CJ product/variant-ID cursor (CJ's `listV2` API is page/size paginated only, no cursor-token param). Window-based: each run processes `CJ_SYNC_MAX_PAGES` pages starting at `cursorPage + 1`. On reaching/passing `totalPages`, reset cursor to 0 (wrap-around) + set `catalogSyncWrappedAt`; otherwise persist the last page processed. Accept page-number drift as a bounded risk (mitigated by idempotent upsert on `externalRef` + periodic wrap-around), not solved by a stronger cursor mechanism.
- **D2 (throughput study — already done, use these exact values unless a real measurement in this session contradicts them)**: cost model is `calls = P·(1+S)` where P=pages, S=page size (1 `fetchVariants` call per product, not per page). Empirical anchor: 100 products/318 variants = 146s real production run → ~1.46s/product. Target ≤60% of 900s timeout = 540s safety budget. **New defaults: `CJ_CATALOG_PAGE_SIZE=100`, `CJ_SYNC_MAX_PAGES=3`** (→ 300 products/run, ~442s estimated, ~49% of timeout). Wire into `backend/serverless.yml`'s SSM-backed `provider.environment` (same pattern as the existing `CJ_DEFAULT_CATEGORY_ID`/`SUPPLIER_AUTO_PROVISION_ENABLED` entries — SSM value with a literal fallback default).
- **D3 (image derivation)**: derive images from `CjCatalogItem.rawPayload` (already `{ product, variant }` raw JSON, confirmed structure) at promotion time via a new shared helper `extractCjImages(rawPayload: unknown): { productImage?: string; variantImage?: string }` — defensively typed, never throws. Do NOT add new structured `imageUrl`/`variantImageUrl` columns to `CjCatalogItem` — this was explicitly rejected in design.md (single source of truth stays `rawPayload`, avoid a second write path that can drift). Only add `bigImage?: string`/`variantImage?: string` to the existing `CjProductDto`/`CjVariantDto` TypeScript interfaces in `cjTypes.ts` (these interfaces are used for typing CJ API responses in `cjClient.ts`, separate from what actually gets persisted to `rawPayload`, which stores the raw untyped object already — the DTO extension is for type-safety/documentation of what fields exist, not a new data path).
- **D4 (promote() image creation)**: inside `promote()`'s existing `prisma.$transaction(async (tx) => {...})` (this file already bypasses repositories for `tx.product.create`/`tx.productVariant.create` — established precedent, follow it): on NEW product creation only, derive product image from the group's first item's `rawPayload.product.bigImage`, set `Product.mainImageUrl` via `tx.product.update(...)` and create a `tx.productImage.create({ sortOrder: 0, ... })`. Per variant created, derive `rawPayload.variant.variantImage`; if present AND different from the product's main image URL, create an additional `tx.productImage.create({ sortOrder: <incrementing> })`. Never create images on the `wasAlreadyPromoted` (re-promotion) path — that's what guarantees no duplicate images on re-runs. Never fail promotion for missing image data (graceful degradation, matches existing `parseSizeColor` best-effort pattern). Never copy `supplierCost` or other internal fields into any public field — unchanged rule.
- **D5 (backfill)**: new one-off script `backend/scripts/backfillCjProductImages.ts` (NOT wired into `serverless.yml`, not a permanent job — manually invoked once via `ts-node` against a target DB). Queries `ProductVariant` with `cjCatalogItemId` set whose `Product` has no `ProductImage`/`mainImageUrl`, reads the already-stored `CjCatalogItem.rawPayload` (zero new CJ API calls), applies the SAME `extractCjImages` helper + image-creation logic as `promote()` (extract that logic so both share it, avoid duplicating the derivation). Idempotent (already-imaged products excluded by the query itself), logs a summary.
