# Adversarial Review Report - cj-catalog-cursor-and-media

- Date: 2026-07-09
- Reviewer: independent Claude Sonnet 5 subagent (fresh context, no implementation history), per `ai-specs/skills/adversarial-review/SKILL.md`
- Initial verdict: **PASS WITH GAPS** (3 Major, 1 Minor, 1 Question)

Run before any production deployment for this change, unlike `cj-catalog-auto-provisioning` where the equivalent review happened after the first production deploy — a deliberate change in ordering given that sibling change's two production incidents.

## Findings and Resolution

| # | Severity | Finding | Resolution |
|---|----------|---------|------------|
| 1 | Major | `cj-catalog-media-capture/spec.md`'s "Variant-specific images are captured..." requirement had no carve-out for the deliberate scope cut (image capture skipped when a variant joins an already-existing product) — the code and tests were correct, but the spec artifact (the source of truth) was silently out of sync with them. | Fixed: added a scenario to `spec.md` explicitly stating the scope cut. Also clarified the "Promoted products receive a main image" requirement's wording to match finding #4's fix (product-image-priority-with-variant-fallback), splitting it into three precise scenarios. |
| 2 | Major | `maxSyncPages`/`catalogPageSize` were parsed via bare `Number(process.env.X ?? default)` with no validation — a misconfigured SSM value (`''`, `'0'`, negative, non-numeric) would make `endPage < startPage`, so the sync loop's `while` never executes: `totalPages` stays `null`, falls back to `1`, and the sync "succeeds" with 0 items and a permanently-frozen cursor, silently, forever. This is exactly the class of numeric-env misconfiguration risk that caused the sibling change's unbounded-defaults incident. | Fixed: added `parsePositiveIntEnv()` (mirrors the existing `getDefaultMarkupMultiplier`'s `Number.isFinite`/`>0` validation pattern already used elsewhere in this codebase), falling back to the safe default and logging a warning on any invalid value. New test: `should_fall_back_to_the_safe_default_window_when_CJ_SYNC_MAX_PAGES_is_invalid` (parametrized over `'0'`, `'-1'`, `'not-a-number'`, `''`). |
| 3 | Major | `updateCatalogSyncCursor` is an unconditional `UPDATE`, not compare-and-swap. Two overlapping `syncCatalog` calls for the same connection (e.g. an admin's manual sync racing the scheduled job — a scenario the shared-CJ-account caveat already documents as possible) could have the later write silently discard the earlier run's more-advanced cursor or `wrappedAt` stamp. | **Accepted as a documented risk, not code-fixed** — impact is bounded (item upserts remain idempotent regardless of cursor bookkeeping; the periodic wrap-around self-corrects any lost cursor progress within one full catalog pass), and a true fix would change `updateCatalogSyncCursor`'s signature/return type, cascading through existing tests, for a narrow-window race with no data-corruption consequence. Documented explicitly in `design.md`'s Risks section as a deferred follow-up, per the reviewer's own suggested alternative. |
| 4 | Minor | A product could end up with `ProductImage` row(s) but a permanently-`null` `mainImageUrl` when only a variant-level image existed (no product-level `bigImage`) — both `promote()` and the backfill script only ever set `mainImageUrl` from the product-level image, never falling back to a captured variant image. This also permanently excluded such a product from the backfill's eligibility query once it had any image row, so the gap could never self-heal. | Fixed: added `planProductImages()` to `cjImageExtraction.ts` — a pure, shared helper that plans the full image set for a pid group (product-level image preferred as main; falls back to the first variant-level image found if no product-level image exists; deduplicates by URL). Rewired both `cjCatalogPromotionService.ts`'s `promote()` and `cjProductImageBackfill.ts`'s `backfillProductImages()` to use it, which also **simplified** both functions (removed per-variant `isNewProduct`/`nextImageSortOrder`/`productMainImageUrl` tracking in `promote()`; removed the first/rest split in the backfill). New tests: 5 in `cjImageExtraction.test.ts` for `planProductImages` directly, plus 1 regression test each in `cjCatalogPromotionService.test.ts` and `cjProductImageBackfill.test.ts` proving `mainImageUrl` is now set from a variant-only image. |
| 5 | Question | `backend/scripts/backfillCjProductImages.ts` reuses the same `Prisma.TransactionClient`-typed helpers as `promote()`. Verified: safe as written (short-lived local/manual `ts-node` process, DB-only transaction work, not inside Lambda) — materially different risk profile from the sibling incident's Lambda-hosted transaction spanning external API calls. No fix needed, but the assumption wasn't documented anywhere. | Documented: added a risk entry to `design.md` and a code comment in the script itself, warning that this transaction-wrapping pattern must be re-validated against a real deployed Lambda before ever being ported into a scheduled job. |
